# Design

## Context

Проект в `D:/Projects/sdr-app` содержит архитектурные материалы, инструкции агентов и свежую структуру OpenSpec. Исходников приложения, CMake, тестов и CI пока нет. Мотивация описана в [proposal.md](proposal.md); поведение — в восьми [delta specs](specs/).

## Goals / Non-Goals

**Goals:** реализовать desktop RX вертикальными срезами, сохранить независимость ядра и контролируемые границы ABI, обеспечить проверяемость аппаратной поддержки и числовой приёмки.

**Non-Goals:** закрыть открытые решения самим фактом планирования, публиковать финальные ABI headers без согласования или гарантировать crash isolation нативных плагинов.

## Decisions

Канонический [архитектурный план](../../../docs/sdr/MVP_V0_1_IMPLEMENTATION_PLAN.md) хранится в `docs/sdr/` по требованию пользователя. Этот документ связывает его с OpenSpec; новые утверждённые ADR здесь не создаются.

- ADR-001/005: независимое C++20-ядро, Qt Quick/QML и гибридный pipeline. Альтернативы из исходного обсуждения — Qt Widgets и универсальный редактируемый DSP Graph; текущая база уже выбирает QML и фиксированную магистраль с точками расширения. Подробные форматы и маршрутизация ещё требуют решений.
- ADR-002: собственный ограниченный docking; альтернатива — сторонняя полноценная система. Точный UX остаётся O-007, без незаметного расширения MVP до IDE.
- ADR-003/004: native SDK Source/Demodulator; альтернатива — isolated host с первого релиза. Здесь принимаются ограничения доверенного процесса и отсутствие гарантии сохранности GUI при аварии. Конкретные ABI-вызовы, память и потоки блокируются O-003/009/010 до реализации SDK.
- ADR-006/011/012: устойчивый RX и latency имеют приоритет, профили 2.4/10/20 MSPS — измерения. Альтернатива — максимизация throughput за счёт очередей и задержки; она не соответствует принятому приоритету. Лимиты очередей и пороги ещё не выбраны.
- ADR-007: аудит фактической поставки, а не только деклараций зависимостей. Выбор FFT/audio/Soapy библиотек выполняется после соответствующих PoC и согласования, без назначения конкретных версий этим change.
- Планирование: один change охватывает предлагаемый MVP целиком, задачи разбиты gates G0–G6. Альтернатива — независимые changes на каждый этап; их можно выделять позднее с переносом требований и задач, избегая двух активных владельцев одного объёма. Этот change не архивируется после одного G0.

Связи модулей, поток данных, очереди, порядок этапов, критерии и карта всех O-ID находятся в каноническом плане. Реализация публичных семантических контрактов из разделов 5–6 baseline требует уточнения: `IInputSource`, `IDemodulator`, `IRadioSession`, `ISpectrumService`, `IRecorder` — проектные интерфейсы, а не утверждённые готовые headers.

## Risks / Trade-offs

- [Нет реального железа в CI] → синтетические/file проверки автоматизируются, аппаратные прогоны имеют отдельные свидетельства и не подменяются mock.
- [Ошибка плагина завершает процесс] → доверенные модули, version negotiation, lifecycle tests; изоляция остаётся после MVP.
- [Неопределённые библиотеки/форматы] → исследовательский PoC и явные точки согласования перед производственной реализацией; O-ID остаются открытыми.
- [Диск/GUI замедляют IQ] → конечные очереди, метрики, тестирование перегрузки; конкретные политики утверждаются до проверки.
- [Baseline смешивает A, R и O в одном ADR] → статус уточнений сохраняется; один VFO и sidecar не становятся принятыми по заголовку ADR.
- [Нет эталонного ноутбука и порогов] → числовая приёмка blocked до O-011/O-012, без фиктивного pass.
- [Крупный change] → проверяемые gates, небольшие задачи и фиксируемые результаты каждого этапа.

## Migration Plan

Миграции существующего приложения нет: разработка с нуля. Сначала G0, затем ранний IQ → FFT → GUI срез, DSP/audio, полноценный GUI и SDK, запись/настройки, финальная аппаратная/релизная матрица. Порядок и допуски к этапам определены планом.

Для будущих форматов настроек/записей предусмотреть версии схем и проверку неподдерживаемых данных; детали утверждаются на G5. До этого не обещать совместимость несуществующего формата. Для отказа от неудачного эксперимента возвращаться к последней проверенной сборке и сохранять пользовательские конфигурации/записи; конкретные механизмы обновлений относятся к O-016.

## Open Questions

Уточнение области приёмки по [ADR-016](../../../docs/sdr/ADR-016-deferred-device-qualification.md): реальные испытания RTL-SDR/Airspy перенесены после MVP пользователем. Существующие адаптеры остаются экспериментальными. Для v0.1 обязательна применимая матрица HackRF; полная будущая O-006 остаётся открытой без блокирования MVP отложенными моделями. На момент ADR-016 Soapy-адаптер был встроен в core и перечислял три семейства явно. Этот аппаратный путь заменён отдельным изменением ADR-017; см. уточнение ниже. Прежний Source SDK остаётся совместимым.

Текущие статусы [O-001…O-020](../../../docs/sdr/OPEN_DECISIONS.md) уточнены 2026-11-07: пользователь утвердил платформы (ADR-013), делегировал технические решения с фиксацией (ADR-014), утвердил эталон, performance и минимальные DSP-критерии (ADR-015). Эти документы уточняют исторические формулировки «ещё не выбрано» выше. Один VFO, CF32/sidecar, ограниченный docking, C ABI и Qt audio теперь приняты в рамках делегации. Архитектура реализации: отдельный headless C++20 core, acquisition worker → очередь 8 неизменяемых CF32-блоков → DSP/record worker, последний snapshot в QML GUI; команды ограничены 32. FFT/FIR собственные, аудио Qt Multimedia mono/48 kHz, SDK v1.0 Source/Demodulator с shared module lifetime и stop перед unload. Публичные контракты — DSP_API.md/PLUGIN_SDK.md в docs/sdr/.

Полная аппаратная матрица O-006 остаётся открытой; O-016/017/018 — после MVP. Решения O-014/O-019 определяют целевой путь, но не закрывают проверки Wayland/HiDPI/portable. Согласованные критерии не считаются выполненными без свидетельств. [Отчёт проверки](../../../docs/sdr/MVP_V0_1_VERIFICATION.md) и tasks сохраняют непрошедшие gates открытыми; change не готов к архивированию.
## Уточнение аппаратной модульности (ADR-017)

Аппаратный путь уточнён отдельным изменением modular-device-providers и [ADR-017](../../../docs/sdr/ADR-017-device-provider-modules.md). Текущее поведение описывает [device-providers](../../specs/device-providers/spec.md): независимые HackRF/RTL-SDR/Airspy DLL/SO, единый Device Provider C ABI, discovery по manifests и отсутствие списка семейств/Soapy-кода в core. Source/Demodulator ABI сохранён. Этот addendum заменяет прежнее описание встроенного Soapy-адаптера выше; длительная и платформенная приёмка остаётся в родительском MVP.

## Task 1.4 — воспроизводимое получение зависимостей (2026-11-08)

Перед реализацией: сохранить существующий baseline vcpkg, зафиксировать SoapySDR 0.8.1 override, добавить машиночитаемый lock Qt 6.10.0 с commit superproject и выбранными gitlinks. Общий Python bootstrap получает исходники в явно указанную внешнюю папку, проверяет pins и устанавливает hardware feature через vcpkg для x64-windows/x64-linux-dynamic. Qt собирается отдельно из зафиксированных исходников либо используется существующий SDK ровно 6.10.0; получение исходников не означает готовый Qt SDK. Документировать команды и фактически проверить чистое получение на Windows 11/MSVC 2022 и Ubuntu 22.04/GCC 11. Целевые среды ADR-013 и независимость модулей ADR-017 не меняются; успешное получение не заменяет GUI/Linux и G6 приёмку. Решения и результаты: docs/sdr/ADR-023-pinned-dependency-acquisition.md и DEPENDENCY_ACQUISITION_VERIFICATION.md.

Уточнение проверки 1.4: Linux port baseline 0.8.1#0 завершал сборку библиотеки, но падал на CMake fixup (ожидал debug/cmake вместо debug/share/cmake/SoapySDR). Локальный overlay 0.8.1#1 исправляет только платформенный CONFIG_PATH, сохраняет исходный tag/SHA-512 и MIT copyright рецепта. Реестр overlay — vcpkg-configuration.json. Получение и сборка SDK проверяются отдельно от GUI; имеющийся Windows MSVC 2026 — дополнительный профиль. Пока чистая MSVC 2022 проверка недоступна, задача 1.4 не отмечается полностью выполненной.
