# Разбор первого RX-прогона и диагностический повтор

Дата: 2026-11-08. Основание: пользователь поручил изучить отчёт, сделать выводы и запустить тест снова. См. [исходный отчёт](RX_ENDURANCE_RUN_2026-11-08.md); пороги ADR-015 остаются прежними.

## Что подтверждено

Все 10250 строк исходного JSONL прочитаны. Первый audio underrun — 2006 s. Счётчик увеличивался в 490 строках, до 520 к 8163 s; это не только последний момент остановки. Audio drops начались отдельно: 9730 s, затем 10001, 10004, 10005, 10016, 10213 и 10250 s; итог 43. Очередь IQ уже достигала глубины 7 задолго до сбоя. В последнем интервале sampled processingMs вырос до 10.597 ms, но одиночные 1 Hz samples не дают maxima всех блоков.

Нулевой displayed FPS — один участок 8187–8302 s, 116 строк. При этом журнал продолжал писаться примерно раз в секунду, а IQ samples монотонно росли. Нельзя приравнивать остановку вывода кадров к остановке DSP; видимость окна не была записана.

Private bytes в последовательных интервалах не показывают постоянного роста: диапазон около 344–350 MiB. Working set достиг 531.652 MiB и позже уменьшился. Это нарушение согласованного лимита, но не доказательство утечки памяти. Средний CPU 1.494% также не исключает коротких stalls.

По разнице первых/последних IQ samples и elapsed clock средний темп около **2399929 IQ/s**, примерно **−29.6 ppm** относительно 2.4 MSPS. Это оценка поступления через буферизованный тракт, не калибровка генератора HackRF. Накопленный дефицит относительно идеального audio clock возможен; фактический темп аудиопотребления раньше не собирался.

Непосредственный механизм stop подтверждён: очередь 8 × 16384 IQ (около 54.6 ms при 2.4 MSPS) не освободила место за дополнительные 20 ms. Harness после fault закрыл процесс с exit 2. WAV-контейнер цел; это не подтверждает качество аудио.

## Проверяемые гипотезы

1. **Расхождение SDR/audio clocks.** Если это причина ранних underrun, produced/delivered/requested frame counters и occupancy должны показать постепенное уменьшение запаса при регулярных callbacks. Случайные read gaps без такого тренда будут свидетельствовать против этой версии.
2. **Редкая задержка writer/DSP/worker.** Если она предшествует IQ overflow, накопительные max DSP/write/block-interval/queue-wait должны резко вырасти возле отказа. Если эти величины остаются малы, нужно исследовать acquisition/runtime отдельно.
3. **Паузы аудиовыхода или окна.** Большой callback gap/state transition объяснит поздние audio drops; hidden/minimized/unexposed окно при работающем DSP объяснит нулевые displayed FPS. Наличие этих событий ещё не доказывает их связь с IQ overflow.

## Условия повтора

Та же частота 100 MHz, HackRF, gain 16, 2.4 MSPS, WFM, native GUI, аудио, WAV, 28800 секунд. Не менять queue capacities, prefill, resampling или thresholds без подтверждения причины. Накопительные maxima ловят короткий stall между 1 Hz строками; audio counters показывают баланс потока; QAudioSink и window state различают вывод и обработку. Физическая audio latency и UI input latency по-прежнему не измерены. Полный повтор — диагностический эксперимент, не заявление об исправлении.

Перед повтором: сборка MSVC, regression accounting, короткий аппаратный RX и проверка WAV/новых метрик. Старый run сохраняется; новый получает отдельный каталог. Исторические документы baseline не переписываются.

## Предварительная верификация

Чистая сборка `build/windows-retry-msvc2026`, MSVC 2026/Qt 6.10.0. Первая серия CTest 7/7 pass. В реальном квалификационном прогоне 60.9997 s: IQ gaps/overflow/audio underrun/drops 0, отображённые спектры минимум 17.00 fps, CPU average 2.158%, память до 532.859 MiB. **Критерий памяти всё ещё нарушен**, это проверка новых измерений, не успешная приёмка. WAV header/data size и audio frame accounting независимо проверены. Max source read 55.17 ms, audio push gap 54.78 ms при max DSP 1.234 ms и writer 0.668 ms: серии выдачи источника видны отдельно от быстрого DSP/записи.

Добавлена регрессия на фактическом Engine/acquisition/queue пути: намеренная 200 ms пауза worker приводит к тому же IQ overflow. До исправления тест обнаружил, что max worker gap не сохранялся, если fault проверялся до следующего pop. Обновление max gap перенесено также перед проверкой failure, чтобы пауза не исчезала при teardown. Это исправление диагностического счётчика; намеренный stall не устанавливает причину первого реального сбоя и не устраняет его.

При stop/new session проверяется сохранение/сброс audio accounting: accepted = delivered + queued + discarded; отдельно учитываются вход, принятые, запрошенные и выданные кадры. Maxima этапов — **wall time**, включающий вытеснение потока планировщиком; высокий writer time сам по себе не доказывает медленный диск. Снимать причинные выводы нужно по совокупности новых показателей.
