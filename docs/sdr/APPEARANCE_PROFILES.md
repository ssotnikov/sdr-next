# Контракт профилей оформления SDR Next v1

Статус: архитектурный контракт и план, **не описание уже реализованной функции**. Основание: ADR-022; OpenSpec support-custom-appearance-profiles. Примеры SDR++ не устанавливают требования к точным именам/цветам его пресетов.

## Независимые слои

| Ресурс | Назначение | Основа |
|---|---|---|
| ui-theme | Окно, header, меню, toolbar, панели, элементы и сообщения | dark + light |
| spectrum-style | Фон спектра, сетка, оси/подписи, trace/traceFill, cursor, readout | dark + light |
| waterfall-style | Фон waterfall, noData, сетка, оси/подписи, cursor | dark + light |
| color-map | Преобразование нормализованной интенсивности в цвет | Независима от основы |

Режим dark/light/system разрешает только основу. Каждый style может явно содержать одинаковые цвета в обоих вариантах: например, всегда тёмный спектр при светлом UI. Смена UI theme не меняет выбранные style/map, их цвета и requested ID.

Встроенные значения: UI builtin:sdr-next, стили графиков builtin:default, карты builtin:next / builtin:ocean / builtin:amber. Фирменные dark/light цвета остаются defaults. Точный дополнительный каталог (Grey Scale, Inferno, Turbo и др.) и аудит его данных не выбраны. Собственная карта из примера не объявляется картой SDR++.

| grid | #26313C | #D6DDE4 |

| cursor | #FFB224 | #FFB224 |

Waterfall builtin:default в обеих основах: background/noData #0A0D10, grid #26313C, labels #A1ADB9, cursor #FFB224. Его подписи располагаются на собственном фоне; общая ось принадлежит явно выбранному графику, а не UI theme. Наличие дополнительных сетки/заливки само по себе не предписывается цветовым профилем: роль применяется к соответствующему элементу renderer. Прозрачность декоративного cursor и параметры измерительной шкалы не меняются выбором карты.

## Файл ресурса

Машинный контракт: appearance-resource-v1.schema.json. UTF-8 JSON, format=1, kind, локальный id и name. id: [a-z0-9][a-z0-9-]{0,63}, name: 1–80 символов. Имя файла не является ID. В реестре ID получает namespace builtin: либо user:, совпадение локального id с builtin не заменяет встроенный ресурс.

Для трёх style/theme видов обязательны variants.dark.colors и variants.light.colors. Пропущенные роли наследуются **только** от встроенного default того же вида и основы. Пользовательское наследование цепочками не поддерживается: нет циклов и ссылок на внешние файлы. Профиль без цветов одного варианта может передать пустой объект colors и получить соответствующий default.

Цвета UI/основных элементов — #RRGGBB. Только traceFill спектра допускает #RRGGBBAA. Это публичный порядок RGBA; Qt #AARRGGBB — внутреннее представление, конвертация явная. Именованные Qt-цвета, системные пути шрифтов, QML/JS, URL/изображения и executable-поля не являются частью формата. Типографика и метрики остаются из brand book. UI-роли trace/traceFill старого BrandTokens не определяют цвета спектра: новый контракт вынес их в spectrum-style.

Color-map задаёт ровно один способ:
- stops: 2–64 объекта {pos, color}, pos строго возрастает от 0 до 1 включительно, первый=0 и последний=1;
- colors: 2–4096 цветов с равномерным положением от 0 до 1.

Цвета карты только #RRGGBB. Интерполяция линейна по кодированным sRGB-каналам, как у текущей Next; это не интерполяция HSV и не линейная яркость. В первой реализации LUT имеет 256 элементов. Больший исходный массив пересчитывается в LUT, не обещая 4096 различимых уровней при 8-bit визуальной интенсивности. Валидные значения вне диапазона clamp к endpoints; NaN/неинициализированные пиксели идут в noData, а не в первый цвет карты.

## Валидация и доступность

Предел ресурса — 256 KiB, вложенность JSON ≤8, до 128 пользовательских ресурсов каждого kind. Неизвестные поля/версия/kind, неверные типы/цвета, нечисловые позиции и нарушенные stops отклоняются до регистрации. Schema покрывает структуру; порядок/endpoints, размеры файлов, квоты и контраст проверяются loader отдельно.

Основные тексты и подписи: контраст ≥4.5:1; границы интерактивных элементов и trace на фоне: ≥3:1, с учётом реально используемых сочетаний. Полупрозрачный fill проверяется после композиции. Декоративные линии сетки не обязаны иметь контраст границы кнопки. Ошибка содержит kind/id/поле/причину и не заменяет текущий snapshot. Плохой файл не блокирует остальные, QML, RX и запуск программы.

## Хранение и UI

Встроенные профили поставляются ресурсами приложения. Пользовательские находятся в appearance/{ui-themes,spectrum-styles,waterfall-styles,color-maps} относительно каталога данных; portable использует appearance/ рядом с executable. Сканирование — при запуске и явном Refresh, без обхода произвольных каталогов. Импорт копирует валидированный JSON в управляемый каталог; исходный файл не меняется. Экспорт сохраняет самостоятельный ресурс v1. Столкновение user ID требует явного выбора замены/нового ID; builtin заменить нельзя.

Панель «Оформление»: режим основы, UI theme, Spectrum style, Waterfall style, Color map с полоской preview. Цветовые редакторы сгруппированы по слоям; доступны Preview, Apply, Cancel, Reset selected layer и Reset all. Встроенный профиль редактируется через сохранение пользовательской копии; пользовательский файл заменяется только явным Save. Apply/экспорт/сохранение используют атомарную запись; Cancel не пишет профиль/выбор. Отдельно выполненный Import добавляет ресурс в каталог, но не делает его активным.

Выбор preview применяется к временному snapshot; Cancel восстанавливает последний применённый snapshot и карту существующей истории. Apply сохраняет ID; нужные пользовательские ресурсы записываются до settings. Сбой settings не повреждает прежний выбор; возможный неиспользуемый ресурс не удаляется автоматически. Импорт, редактирование и применение блокируются действующими endurance guards. Смена системного оформления обрабатывается как сейчас Qt; критерии длительного теста не пересматриваются.

## Настройки и миграция

Новый объект settings.appearance: {format:1, mode, uiThemeId, spectrumStyleId, waterfallStyleId, colorMapId}. Внешняя settings schema_version=1 сохраняется: изменение аддитивно. Текущий предел settings-файла 64 KiB не увеличивается из-за коллекции профилей. Цветовые определения хранятся в ресурсах, не разрастаются в настройках окна.

Старые theme=0/1/2 → dark/light/system; palette=0/1/2 → builtin:ocean/amber/next. При отсутствии palette выбирается Next. Старый accent сохраняется: при отличии от defaults создаются миграционные пользовательские копии UI и cursor-цветов графиков, а не глобальная привязка будущих пользовательских тем. Существующие ресурсы с другим содержимым не перезаписываются; применяются уникальные стабильные ID. Прочие настройки окна, источника, частоты, записей и docking не меняются.

Отсутствующий/неподдерживаемый ID сохраняется как requested; resolved snapshot использует fallback только своего слоя, UI показывает «профиль недоступен». Возвращённый файл снова разрешается по ID. Неподдерживаемый appearance.format не перезаписывается обычным сохранением других настроек; пользовательский reset — отдельное явное действие.

## Внутренние границы

| Контракт | Ответственность |
|---|---|
| ResourceLoader.parse(bytes) | Ограниченный разбор, структурная и семантическая проверка; типизированный ресурс или ошибка |
| AppearanceCatalog.list(kind) | Встроенные и валидные пользовательские профили со стабильными ID |
| Catalog.import/export | Управляемые файлы, namespace, atomic write; без изменения текущего RX/выбора |
| AppearanceResolver.resolve(selection, resolvedBase) | Immutable snapshot: uiColors, spectrumColors, waterfallColors, colorMapLut, requested/resolved IDs и diagnostics |
| AppearanceSession.preview/apply/cancel/reset | Транзакция оформления и persistence; в endurance недоступна |
| Renderer.applyAppearance(snapshot) | Обновление только визуальных материалов/текстур; без device reconfigure, изменения DSP и остановки RX |

Это приватные интерфейсы GUI, не Plugin SDK/C ABI. Названия классов уточняются реализацией без изменения внешних семантик. JSON читается и LUT готовится вне DSP/device callback. Snapshot публикуется целиком, без смешивания разных версий цветов. Каталог хранит metadata, а не все полные JSON/массивы цветов. Файловое сканирование и разбор выполняются последовательно на вспомогательном worker, без блокировки render callback; GUI получает готовые результаты. Кэш ограничен восемью разрешёнными ресурсами (текущий и preview), а не числом файлов в каталоге.

## История waterfall и проверка производительности

Текущий SpectrumItem хранит RGB и очищает history при setColorMap. Это требуется заменить: хранить квантизованную интенсивность 0..255 плюс бит валидности (только визуальная история), а цвет получать из текущей LUT. Окно 2048×256 требует около 576 KiB для уровней+валидности сверх/взамен текущего RGB-кэша; точный суммарный CPU/GPU footprint измеряется. RGB-кэш допускается, но пересчитывается из уровней при смене карты; данные/порядок строк не теряются.

Исходный FFT frame для линии спектра, IQ-запись и DSP precision не квантуются этим буфером. Шкала dB и действующая нормализация не меняются при выборе карты. noData и background — отдельные роли waterfall; background не подменяет валидный минимальный сигнал. После изменения цветов обновляются вся история, оси и overlay соответствующего графика.

Приёмка: unit loader/resolver/миграция, QML независимость и persistence, synthetic RX без перезапуска, recolor/cancel с сохранением строк, CPU/GPU/software fallback и память/FPS/UI latency на reference. Обязательные численные критерии ADR-015 остаются прежними, прежние провалы не превращаются в pass. Нативная проверка заголовка add-branded-window-header остаётся отдельной открытой работой.

## План реализации

1. Типы ресурсов, loader/validator, schema/example fixtures, unit tests.
2. Каталог builtin/user, import/export, ID и восстановление после плохого файла; файловые тесты.
3. Resolver/session, profile selection и безопасная миграция настроек; тесты независимости и fallback.
4. Раздельные binding UI/spectrum/waterfall и интенсивностная история; rendering/recolor tests.
5. Панель оформления, preview/apply/cancel/reset, RU/EN и endurance guards; QML tests.
6. Windows MSVC/CTest, Linux и native/render/benchmark отчёт; только после выполнения — sync/архив OpenSpec.

Пока runtime не реализован, ни импорт, ни custom-профили не объявляются доступными пользователю. Прямой импорт форматов SDR++, hot reload и набор дополнительных встроенных карт — отдельные неутверждённые расширения.

Срок включения в релиз и приоритет относительно оставшегося MVP не согласованы: AP-O-001. Дополнительные каталоги, чужие форматы и hot reload учитываются в OPEN_DECISIONS.md (AP-O-002…004).

## Сохранённая схема Classic Teal

Пользователь выбрал сохранение прежней сине-серой схемы с бирюзовым акцентом. В будущем каталоге предусмотрены ui-theme, spectrum-style и waterfall-style с ID builtin:classic-teal; выбираются независимо. Основной default builtin:sdr-next не меняется. Примеры тех же ресурсов для пользовательского импорта: examples/appearance/classic-teal.*.json; при таком импорте namespace будет user:classic-teal. Карта — существующая builtin:ocean, отдельный импорт копии карты не требуется.

Тёмная основа восстановлена по скриншоту и прежним Main.qml/spectrum_item.cpp (6a15e2c): base #16232F, surface #1E303E, ink #E2EBED, muted #9BAEB8, accent #72D5D2; графики #101C2C, trace #7EE4E0, readout #E8B979. Фоны #1E303E и #101C2C дополнительно сверены с PNG. readout — отдельная необязательная роль spectrum-style для сохранения тёплого цвета числового уровня, независимо от бирюзовой линии. Она наследует defaults при отсутствии в файле.

Это адаптация цветовой схемы, не пиксельная копия старого Fusion UI: новые hover/border/status роли сопоставлены с контрактом и проверяются на контраст; legacy градиенты кнопок/разные цвета двух осей не кодируются этой версией профиля. Светлый UI — адаптация прежней светлой основы с контрастным тёмно-бирюзовым dialInk, не вариант, показанный на скриншоте. Спектр и waterfall оставлены тёмными в обеих основах, как в прежних исходниках. Название SDR Next, современный заголовок и IBM Plex не откатываются.
