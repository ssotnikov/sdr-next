# Протокол длительного Windows RX

Дата: 2026-11-08. Основание: ADR-015 и поручение пользователя начать восемь часов испытаний. Пороги и scope MVP не изменяются.

Режим запускается явно: `sdr_app --endurance-dir <fresh-directory> --endurance-seconds 28800 --endurance-provider device:org.sdr.device.hackrf:`. Требуются подключённый HackRF, совместимый внешний runtime, native Windows GUI и доступный аудиовыход. Профиль: 2.4 MSPS, 100 MHz, WFM, gain 16, PPM 0, Bias-T off, direct sampling off. WAV mono PCM16 48 kHz около 2.8 GB; Raw IQ около 553 GB не записывается. Небольшая громкость не отключает аудиотракт.

Отсчёт начинается после подтверждения RX/audio/WAV. Нормальное завершение останавливает запись и RX, дожидается остановки и сохраняет итоговый JSON. Сырой JSONL сбрасывается на диск каждую секунду; отсутствие summary или ручное закрытие означает незавершённость. Диагностика и пользовательские артефакты остаются локально вне Git. Физические серийные номера не включаются в отчёт.

CPU измеряется по process time / wall time / logical processors. RAM: working set и private bytes; сохраняется максимум обоих показателей. Spectrum FPS — изменившиеся спектры, дошедшие до frameSwapped, а не просто число DSP FFT. Логируется также доставка новых спектров в GUI. Queued ping из отдельного потока раз в 250 ms измеряет задержку GUI event queue; p95 является proxy, не подтверждением реакции на реальный пользовательский ввод. Физическая RF→audio latency требует отдельного контрольного сигнала и остаётся not_verified. Нулевые underrun не доказывают слышимость.

После неуспешного теста окно остаётся открытым с FAILED и причиной; summary уже сохранён. Измерения/probe останавливаются и запрет автоматического сна снимается сразу после завершения теста. Runner отмечает `failed_window_open`, затем ожидает закрытия окна; итог теста хранится отдельно от exit code процесса. Прежние прогоны до этого изменения автоматически закрывали окно при failure.

Во время измерений панели настройки и shortcuts Space/Escape/Ctrl+O отключены, чтобы случайный ввод не менял сеанс; закрытие окна остаётся способом явного прерывания. В обычном режиме shortcuts доступны, autoRepeat для Space/Escape выключен. Автоматический сон/гашение экрана предотвращаются только пока измеряется тест; power plan не меняется. Потеря AC фиксируется как отклонение эталона. Тяжёлые сборки перед основным прогоном завершаются.

Даже завершённый чистый прогон даёт частичный verdict: остаются отдельные измерения UI input и audio latency, Windows 10/Linux, 10/20 MSPS и остальные gates MVP. Запуск теста не является его завершением.

## Короткое сравнение рендеринга и замер ввода

На эталонном Windows-ноутбуке выполнены короткие прогоны HackRF 2,4 MSPS, WFM, с записью WAV, видимым окном и питанием от сети. Графический вариант использует [ADR-026](ADR-026-waterfall-upload-budget.md).

| Профиль | Пиковый RAM, MiB | Пик private bytes, MiB | Минимум свежего спектра, кадр/с | Audio underrun |
| --- | ---: | ---: | ---: | ---: |
| Исходный D3D11, 60 с | 531,80 | 351,66 | 16,00 | 2 |
| Кольцо текстур и расписание FFT, D3D11, 60 с | 544,09 | 345,34 | 16,99 | 0 |
| Та же сборка с OpenGL, 61 с и пробой ввода | 615,46 | 426,74 | 17,97 | 0 |

Во всех трёх запусках не зарегистрировано разрывов или переполнений IQ и отклонённых аудиоблоков. Новая сборка прошла 8/8 CTest, включая проверку последовательности строк waterfall после оборота кольца. Короткое сравнение подтверждает улучшение минимума FPS на этом интервале. Пик RAM остаётся выше 512 MiB. Снимок рабочего набора новой сборки около 543,84 MiB включал 276,70 MiB приватных страниц, 207,53 MiB отображённых областей и 59,61 MiB образов. Принадлежность основных отображённых областей не установлена. OpenGL увеличил пик и не выбран для приёмки.

В отдельном прогоне D3D11 под активным приёмом 40 событий колеса были отправлены через Win32 `SendInput`. Завершение замера — первый снимок рабочего стола, где частотная шкала совпала с ожидаемым изображением после масштабирования. Медиана 63,28 мс, p95 82,55 мс, максимум 82,77 мс. Замер включает доставку ввода, обработку и обновление видимых пикселей с задержкой их опроса. Он покрывает действие масштабирования спектра. Файлы сравнения и замера находятся в локальных каталогах `build/endurance/20261109-143331-render-baseline`, `20261109-145042-render-tiled`, `20261109-145218-render-opengl` и `20261109-145340-render-native-ui`.

## Профиль памяти по этапам

Копии одного бинарника `e936892` запущены с переносимыми настройками в локальном каталоге `build/endurance/20261109-150741-memory-stages`. Окно 1280×790, Qt 6.10, D3D11. Для контроля без устройств DLL и manifest не копировались. В каждом состоянии снимались текущий рабочий набор и частная память примерно пять раз в секунду на протяжении 5–7 с. Эти значения отражают максимумы выборки, а не максимум за жизнь процесса.

| Состояние | Пиковый рабочий набор, MiB | Пик private bytes, MiB |
| --- | ---: | ---: |
| Окно без модулей, приём остановлен | 521,65 | 313,86 |
| Синтетический IQ 2,4 MSPS без модулей | 528,75 | 318,47 |
| Окно после обнаружения HackRF, приём остановлен | 544,32 | 331,94 |
| HackRF 2,4 MSPS без записи, вкладка приёма | 552,73 | 340,32 |
| HackRF без записи, вкладка файлов | 554,91 | 342,68 |
| HackRF с WAV, та же вкладка | 555,43 | 343,53 |

Синтетический приём в этом опыте сопровождался audio underrun и использован только как контроль памяти. Для HackRF оба этапа с вкладкой файлов выполнены в одном процессе. WAV после завершения читается до последнего отсчёта.

`QueryWorkingSet` и `VirtualQueryEx` показали около 207 MiB резидентных отображённых областей уже в окне без модулей. По путям `GetMappedFileNameW` из них 197,38 MiB относятся к TTF, 7,50 MiB к TTC и 0,08 MiB к OTF. На том же бинарнике при неизменном D3D11 пик окна без модулей составил 514,90 MiB в штатном режиме, 101,66 MiB с `QT_QPA_PLATFORM=windows:fontengine=gdi` и 100,51 MiB с `windows:fontengine=freetype`. В снимке GDI резидентные отображения TTF/TTC занимали 1,11 MiB. Это локализует основной эффект в выборе шрифтового режима Qt. [Счётчики памяти Windows](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex) · [Разбор параметров Windows-плагина Qt 6.10](https://github.com/qt/qtbase/blob/v6.10.0/src/plugins/platforms/windows/qwindowsintegration.cpp#L133-L141)

Изолированный прогон GDI/D3D11 с HackRF 2,4 MSPS, WFM и WAV завершился через 60 с. Все 60 секундных снимков сделаны при видимом окне и питании от сети. Пик RAM 124,61 MiB, private bytes 119,32 MiB, минимум свежего спектра 17,00 кадра/с. Разрывов, переполнений и аудиоошибок не зарегистрировано. Русские подписи, спектр и waterfall проверены визуально. Режим задавался только для диагностического процесса. Перед выбором штатного режима нужно проверить шрифты и интерфейс на поддерживаемых Windows и повторить короткий аппаратный профиль на релизной конфигурации.

## Физическая задержка RF→аудио

tinySA Ultra может подавать контрольный RF-сигнал с модуляцией. Для повторяемого замера нужны RF-переход с опорным фронтом и запись аналогового аудиовыхода на той же временной шкале. У двухканального FNIRSI DS215H полоса 50 МГц. На 100 МГц в опорный канал подают огибающую с подходящего RF-детектора, в другой канал подают звук с выхода ноутбука. Переход должен быть виден в обеих записях. Для профиля WFM можно включать уже модулированную несущую и измерять задержку до появления контрольного тона. Провести несколько повторов при уже работающем RX и зафиксировать настройки и критерий выбора фронта. Одноканальный FNIRSI DSO-510 не даёт одновременно записать две точки. Физический замер пока не выполнен. [tinySA Ultra](https://tinysa.org/wiki/pmwiki.php?n=TinySA4.MenuTree) · [FNIRSI DS215H](https://www.fnirsi.com/products/ds215h) · [FNIRSI DSO-510](https://www.fnirsi.com/products/dso-510)

## Проверка сохранения окна при ошибке

2026-11-08: MSVC 2026 сборка и CTest 7/7 pass, включая QML guard controls. Для native GUI намеренно задан отсутствующий provider в `build/endurance/window-preservation-check`. После 15 s startup failure появился `summary.json` со state=failed, процесс остался жив, в окне видны FAILED и причина. Через UI проверены Space/Escape: окно остаётся, RX не запускается. Затем окно закрыто явно, ordinary SDR Next вновь открыт с доступными контролами. Это проверка поведения ошибки, не аппаратный burn-in. Runner дополнительно проверен синтаксическим разбором; его ветка `failed_window_open` не проверялась отдельным полным end-to-end запуском wrapper в этой проверке.
